# MuseTalk 后端性能优化与 PTS 卡顿修复

> 日期：2026-06-09
> 分支：refactor/video-pip

---

## 一、问题现象

前端播放严重卡顿，日志显示实时倍率仅 **0.85~0.87x**（< 1.0x = 推理跟不上播放）：

```
[perf] sentence_id=5 推理完成 | 帧数=62 | 音频=2.48s | 推理耗时=2.891s | 实时倍率=0.86x
```

优化推理性能后（实时倍率提升至 3.5~4.75x），前端仍然卡死，定位为 PTS 时钟错位问题。

---

## 二、性能优化（3 项）

### 2.1 BATCH 16 → 48

**文件**：`services/musetalk_engine.py`

```python
# 修改前
BATCH = 16

# 修改后
BATCH = 48
```

**效果**：62 帧从 4 batch 降到 2 batch，减少一半的 CUDA kernel launch / 事件记录 / yield 调度开销。per-frame 耗时从 ~5.3ms 降至 ~4.1ms（-23%）。

### 2.2 去掉全量 `torch.cuda.synchronize()`，修复流水线重叠

**文件**：`services/musetalk_engine.py` → `generate_frames()`

原有两处 `torch.cuda.synchronize()` 阻断了 UNet/VAE 双 CUDA 流的流水线重叠：

| 位置 | 修改前 | 修改后 |
|------|--------|--------|
| UNet forward 之后 | `torch.cuda.synchronize()` 全量同步 | `unet_done.synchronize()` 仅等事件，不阻塞 vae_stream |
| VAE+blend 之后 | `torch.cuda.synchronize()` 全量同步 | **删除**，让下一批 UNet 输入准备与当前批 VAE decode 在 GPU 上重叠 |

同时调整了 yield 顺序：先 yield prev_blend（CPU 端触发 H264 编码），再做 UNet 计时。使得 CPU 端 H264 编码、GPU 端 VAE decode、GPU 端下一批 UNet 输入传输三路并行。

### 2.3 H264 编码器跨句复用

**文件**：`api/ws_routes.py`

```python
# 修改前：每句话创建新编码器
async with engine._lock:
    encoder = H264StreamEncoder(width=TARGET_W, height=TARGET_H, fps=FPS)

# 修改后：连接级别创建，跨句复用，每句 close() 后重建
encoder = H264StreamEncoder(width=TARGET_W, height=TARGET_H, fps=FPS)  # 连接初始化时

# 每句结束后重建（保证首帧为 IDR + SPS/PPS）
encoder.close()
encoder = H264StreamEncoder(width=TARGET_W, height=TARGET_H, fps=FPS)
```

避免每句话重复执行 `_nvenc_available()` 探测 + libx264 初始化（约 10~20ms）。

### 优化效果

```
# 优化前
[perf] sentence_id=5 推理完成 | 帧数=62 | 音频=2.48s | 推理耗时=2.891s | 实时倍率=0.86x

# 优化后
[perf] sentence_id=5 推理完成 | 帧数=74 | 音频=2.96s | 推理耗时=0.830s | 实时倍率=3.57x
```

实时倍率从 **0.86x → 3.57x**，GPU 推理完全不再是瓶颈。

## 三、PTS 卡顿修复（1 项）

### 3.1 问题根因

优化后前端仍然卡死。定位到 **服务端全局 PTS 与客户端句切换 flush 之间的时钟错位**：

**服务端**（修改前）：
```python
# ws_routes.py — 全局 PTS 跨句累积
global_pts_offset_ms += audio_duration_ms  # 每句结束时递增
pts_base_ms = global_pts_offset_ms          # 每句 PTS 从累积值开始
```

- sentence_id=4 的 PTS：0, 40, 80, ... 2440ms
- sentence_id=5 的 PTS：2480, 2520, 2560, ... （从 2480ms 开始）

**客户端**（修改前）：
```java
// ChatActivity.java — 句切换调用 sentenceTransitionFlush()
videoDecoder.sentenceTransitionFlush();
```

`sentenceTransitionFlush()` flush MediaCodec 但 **不重置** `baseRenderNs` / `basePtsUs`（渲染时钟锚点）。

**时钟错位链路**：
1. sentence_id=4 首帧 PTS=0 → `basePtsUs = 0`，`baseRenderNs = now + 100ms`
2. 句切换 → `sentenceTransitionFlush()` → flush codec，但 `basePtsUs` 仍为 0
3. sentence_id=5 首帧 PTS=2480ms → `sinceBaseUs = 2480000 - 0 = 2480000`
4. `targetNs = baseRenderNs + 2480000 * 1000 = now + 2480.1s`（远在未来）
5. 所有帧的 `targetNs` 都远超当前时间 → 帧堆积在 MediaCodec 输出缓冲区 → 画面卡死

### 3.2 修复方案

**原则**：每句 PTS 从 0 开始 + 客户端 flush 时重置时钟锚点。

#### 服务端（`api/ws_routes.py`）

```python
# 修改前
global_pts_offset_ms += audio_duration_ms
pts_base_ms = global_pts_offset_ms

# 修改后
pts_base_ms = 0  # 每句 PTS 从 0 开始
# 删除 global_pts_offset_ms 相关代码
```

#### 客户端（`ChatActivity.java`）

```java
// 修改前
videoDecoder.sentenceTransitionFlush();  // 不重置 baseRenderNs/basePtsUs

// 修改后
videoDecoder.flushForNewSentence();  // 重置 baseRenderNs/basePtsUs/lastActualRenderNs
```

### 3.3 `flushForNewSentence` vs `sentenceTransitionFlush`

| 方法 | flush codec | 清空 pendingAUs | 重置 baseRenderNs/basePtsUs | 适用场景 |
|------|:-----------:|:---------------:|:---------------------------:|----------|
| `sentenceTransitionFlush()` | ✅ | ✅ | ❌ | PTS 跨句连续时 |
| `flushForNewSentence()` | ✅ | ✅ | ✅ | PTS 每句从 0 开始 |

本次修复使用 `flushForNewSentence()`，因为服务端已改为每句 PTS 从 0 开始。
