## <a id="sec-1" name="sec-1">​</a>1. 产品概述
### 1.1 产品定位

AI 数字人导游是一款面向景区、博物馆、主题乐园等场景的**智能导览系统**。系统以 **AI 数字人** 为核心交互载体，通过 Android 客户端为用户提供自然语言对话式的导游讲解服务，并叠加 **AI 个性化路线推荐**，让游客获得"随身 AI 导游 + 智能游览规划"的沉浸式体验。

### 1.2 核心价值

| 维度 | 说明 |
| --- | --- |
| **沉浸式交互** | AI 数字人口型同步（H.264 实时视频流）、实时语音合成，提供"面对面"讲解体验 |
| **多模态输入** | 支持文本、语音（NLS 实时转写 + 实时字幕）、前置摄像头面部表情分析等交互方式 |
| **知识驱动** | 基于 RAG 技术，将景区资料文档转化为可检索的知识库，确保回答准确有据 |
| **智能规划** | AI 依据用户偏好从知识库结构化生成游览路线，前端以"灵动岛数轴"展示，结合 GPS 自动判定到达 |
| **智能化管理** | 管理员端提供游客情感分析、面部表情分析、热门问题排行、AI 服务建议等数据驾驶舱 |
| **可扩展架构** | 算力分离部署，AI 推理服务独立伸缩，支持多景区横向扩展 |

### 1.3 用户角色

| 角色 | 职责 |
| --- | --- |
| **游客（C 端用户）** | 浏览景点、与 AI 数字人导游对话、生成并跟随个性化路线、查看与评价旅游历史 |
| **景区管理员（B 端用户）** | 管理景点信息、上传知识文档、配置数字人形象与音色、查看数据统计分析 |

### 1.4 终端形态

- **前端**：Android 原生应用（Java，View Binding，MVVM；微信式聊天界面 + 数字人视频渲染 + 灵动岛路线数轴）
- **后端 API**：Spring Boot RESTful + WebSocket 服务
- **管理后台**：集成于 Android 管理端

### 3.2 游客端功能详述

#### 3.2.1 用户认证

- **注册**：账号 4-16 位字母/数字/下划线，密码 6-20 位，昵称 1-20 字符
- **登录**：返回 JWT Token（HS256/384/512，由密钥长度自适应）+ 用户雪花 ID
- **鉴权**：所有非登录/注册接口通过 `UserJwtInterceptor` 拦截，Token 存 Redis（7 天过期，剩余 < 24h 自动续期）
- **上下文**：`UserContext`（ThreadLocal）在请求生命周期内持有用户 ID，请求结束自动清理

#### 3.2.2 AI 导游对话

核心交互入口，通过 WebSocket 长连接实现**实时双向通信**。一条 WS 连接同时承载：对话、语音、视频、路线、面部表情五类业务。

```
客户端 ──WebSocket──► Java 后端 ──WebSocket──► CosyVoice (TTS)
                       │    ▲                        │
                       │    ├── Redis (向量检索+画像) │ PCM
                       │    ├── DashScope (LLM)       ▼
                       │    ├── 阿里云 NLS (语音识别)  MuseTalk (数字人 H.264)
                       │    └── MySQL (聊天记忆)
```

**会话标识**：新会话由 `ChatSessionContext` 生成 `conversationId = UUID`；从历史记录继续对话时，客户端可在握手中携带已有 `conversationId`。后端先按“当前用户 + conversationId”校验历史记录归属，校验通过则沿用并衔接 LLM 记忆与游览历史，失败则移除该参数并创建新 UUID。服务端在 `allDone` 中回传权威 `conversationId`。当前校验未同时约束 `attractionId`，同一用户跨景点复用 ID 可能混合旧对话记忆与当前景点上下文，属于已知实现限制。

**消息类型矩阵：**

| type | 方向 | 载体 | 说明 |
| --- | --- | --- | --- |
| `text` | 客户端→后端 | Text (JSON) | 文本输入（触发 `resetSpeakRound`，重置说话轮次） |
| `micOn`/`micOff` | 客户端→后端 | Text (JSON) | 麦克风开关（创建/停止 NLS 识别器） |
| `emotionFrame` | 客户端→后端 | Text (JSON, Base64) | 前置摄像头面部表情帧，送 vision 模型分类；每用户每 5 秒最多 1 次（令牌桶限流） |
| `interrupt` | 客户端→后端 | Text (JSON) | 主动打断数字人（`resetSpeakRound` + 停 TTS + MuseTalk + 重建 TTS 线程池） |
| `routeGenerate`/`routeArrive`/`routeClose` | 客户端→后端 | Text (JSON) | 路线推荐控制（见 3.2.5） |
| `ping`/`pong` | 双向 | Text (JSON) | 心跳检测 |
| `allDone` | 后端→客户端 | Text (JSON) | WS 连接建立、MuseTalk/CosyVoice 下游连接就绪 |
| `ready` | 后端→客户端 | Text (JSON) | MuseTalk 数字人 avatar 预热完毕 |
| `speechStarted` | 后端→客户端 | Text (JSON) | NLS 检测到一句话开始 |
| `interimText` | 后端→客户端 | Text (JSON) | NLS 中间识别结果（实时字幕） |
| `userInput` | 后端→客户端 | Text (JSON) | NLS 一句话最终识别文本（触发 `resetSpeakRound`） |
| `aiOutput` | 后端→客户端 | Text (JSON) | AI 文本回复（按标点逐句推送） |
| `responseDone` | 后端→客户端 | Text (JSON) | LLM 流式回复完成通知；后端据此标记 `llmRoundComplete` |
| `done` | 后端→客户端 | Text (JSON) | 单句视频生成完毕 |
| **`speakingDone`** | 后端→客户端 | Text (JSON) | **本轮数字人说话收尾**：LLM 已结束且待出镜句数为 0 时，经 `OutboundPacer` 排在末帧之后下发，触发客户端 EOS 排空 → 闭嘴待机（v4 新增，见 4.1/4.8） |
| `routeTimeline`/`routeUpdate`/`routeClosed`/`routeError` | 后端→客户端 | Text (JSON) | 路线推荐结果（见 3.2.5） |
| `error`/`connectionError` | 后端→客户端 | Text (JSON) | 错误通知 |
| 音频帧（首字节 `0x01`） | 后端→客户端 | Binary | TTS 音频：`0x01` + sentenceId(2B) + ptsMs(4B) + PCM (16kHz s16le mono)，共 7 字节 header |
| 视频帧（首字节 `0x03`） | 后端→客户端 | Binary | 数字人 H.264：`0x03` + sentenceId(2B) + ptsMs(4B) + keyFrame(1B) + H.264 AU，共 8 字节 header |
| 裸 PCM | 客户端→后端 | Binary | 麦克风采集音频（送 NLS 转写） |

> **轮次语义**：一次用户输入 = 一个「说话轮次」。轮次内可能含多句（LLM 按标点拆分，逐句走 TTS→MuseTalk）。后端用 `pendingSpeakSentences` 计数待出镜句数，每句 TTS 调度时 `+1`、MuseTalk 单句 `done` 时 `-1`；当 LLM 流结束 **且** 待出镜归 0，才经 Pacer 下发 `speakingDone`，保证末帧不丢、收口后客户端才闭嘴。

#### 3.2.3 景点浏览

- 基于地理位置的游标分页（按距离排序），支持关键词/类型筛选
- 返回景点 ID、名称、封面图、类型、距离
- 用户点击景点进入 WebSocket 对话（连接参数：`token` + `attractionId`，继续历史对话时可附带 `conversationId`）

#### 3.2.4 旅游历史与评价

- 游标分页展示历史对话记录，支持关键词搜索、类型筛选和状态筛选
- 支持单条删除、评分评价（1-5 分 + 文字反馈）
- 会话状态流转：`进行中(0) → 已结束(1) → 已评价(2)`；WS 断连初始为进行中，用户点击"结束对话"→ `PUT /v1/users/tourHistory/{conversationId}/end` 变为已结束，提交评价后联动变为已评价
- WS 建立成功时同步创建或复用 `tour_status=0` 的游览历史，使主页可立即展示；断开时仅“提问过 或 连接 ≥30s”的会话通过 RabbitMQ 更新消息数并创建待评价记录。零提问且连接不足 30 秒的记录仍保留为 `IN_PROGRESS`，待用户继续对话或显式结束时按零交互规则清理

#### 3.2.5 AI 路线推荐（灵动岛数轴）

依据用户个性化偏好，由 AI 从知识库文档中**结构化输出一串有序地标**，前端以"灵动岛"数轴形式展示（含 未到达/进行中/已到达 三态）。

- **承载通道**：路线生成与进度更新复用数字人对话的 WebSocket（`/chat`）；路线数据按 `attractionId + userId + conversationId` 存入 Redis，TTL 为 12 小时。WS 断开只清理连接资源，不自动删除路线。
- **坐标系**：地标坐标由后端调用高德 Web 服务预解析，统一返回 **GCJ-02（火星坐标）**；前端定位与到达判定**必须统一使用高德坐标系**，切勿混用系统原生 GPS（WGS-84），否则有数十~数百米偏移。
- **到达判定**：前端用高德定位 + 地标坐标做距离检测，判定到达后通过 `routeArrive` 回报后端持久化并前移指针；保留**手动点选兜底**（室内/密集地标 GPS 不可靠时）。
- **降级**：未配置高德 Key / 配额超限 / 某地标解析失败时，对应节点 `resolved=false`、坐标为空，路线仍正常下发，前端回退为按地标名定位。
- **REST 恢复**：刷新/重连后通过 `GET /v1/users/route/current?attractionId=<id>&conversationId=<uuid>` 恢复对应会话的激活路线；`attractionId` 与 `conversationId` 均为必填参数。
- **显式关闭**：客户端发送 `routeClose` 后，后端删除当前会话的路线及生成状态并返回 `routeClosed`。

**交互消息：**

| 方向 | type | 载荷 | 说明 |
| --- | --- | --- | --- |
| 入站 | `routeGenerate` | 无 | 触发生成个性化路线（异步，专用线程池） |
| 入站 | `routeArrive` | `stopIndex` | 上报某节点已到达，前移当前指针 |
| 入站 | `routeClose` | 无 | 关闭并清除当前路线 |
| 出站 | `routeTimeline` | `data: RoutePlanVO` | 路线生成成功，下发完整数轴 |
| 出站 | `routeUpdate` | `data: RoutePlanVO` | 节点到达后下发更新后的数轴 |
| 出站 | `routeClosed` | 无 | 路线已关闭 |
| 出站 | `routeError` | `text` | 无资料 / 生成失败 / 无可更新路线 |

```

### 4.1 AI 导游对话全链路

```
                    Android                      Java 后端                      AI 服务
                       │                            │                             │
  ── 建立连接 ──►  WS /ai-project/chat?token=&attractionId=&conversationId=       │
                       │                            │                             │
                       │                    1) 握手 JWT 鉴权 (query/Header)        │
                       │                    2) 校验可选 conversationId 的用户归属  │

                       │                       (沿用合法 ID，否则生成 UUID)        │
                       │                    3) 缓存用户画像 → Redis               │
                       │                    4) 连接 MuseTalk WS ──────────►  init + 预加载头像
                       │                    5) 连接 CosyVoice WS ─────────►  init + 加载音色
                       │                    6) 创建 OutboundPacer (PTS 节拍发送器)
                       │  ◄── allDone ────          │                             │
                       │                            │                             │
  ── 文本输入 ──►  {"type":"text","text":"..."}     │                             │
                       │                    0) resetSpeakRound()  ← 新一轮计数清零
                       │                    1) 令牌桶限流检查 (每用户每分钟10次)   │
                       │                    2) 递增提问计数 (标记有效会话)         │

                       │                       • RAG 文档检索 (Redis Vector)       │
                       │                       • 对话历史 (JDBC, 最近10轮)          │
                       │                    4) 调用 llmGuideChatClient (DashScope) │

                       │                       ┌─ 逐句下发 aiOutput ──► 显示文本   │
                       │                       │  └─ beginSpeakSentence() +1 ─┐    │
                       │                       │  └─ 逐句投递 TTS ────► synthesize│
                       │  ◄── 音频帧(0x01+PCM) │◄── 7B header + PCM ◄───────────  │
                       │  (AVSyncPlayer 播放)   │  └ 剥离 header 的裸 PCM 整句────► MuseTalk
                       │                       │                       audio_end 触发推理
                       │  ◄── 视频帧(0x03+H264)│◄────── H.264 AU 流 ◄───────────  │
                       │  (MediaCodec 解码渲染) │  (含编码器尾包保发，收口 AU 必发)   │
                       │                       │                                   │
                       │                       │  (OutboundPacer 按 PTS 节拍下发)    │
                       │  ◄── responseDone ──  │  (LLM 流结束)                     │
                       │                       │   markLlmCompleteAndMaybeReady()  │
                       │  ◄── done(单句) ────  │  onSpeakVideoDoneAndMaybeReady()  │
                       │                       │  (每句 MuseTalk done 时 -1)       │
                       │                       │                                   │
                       │  ◄── speakingDone ──  │  (LLM 结束 且 待出镜=0 → Pacer 末帧后下发)
                       │  (AVSyncPlayer → EOS 排空 → onSpeakingEnd → 闭嘴待机)
```

> **音画同步（客户端 AVSyncPlayer）**：音视频在后端为**纯透传**（不排队、不同步），Jitter Buffer 与同步职责下放客户端。前端以音频播放位置为主时钟，按帧 PTS 对齐 H.264 视频帧（25fps / 40ms 一帧），中后期队列饿死或撑爆时按策略丢帧，保证口型与语音对齐。后端 `OutboundPacer` 在出站侧按 PTS 时钟节拍下发视频帧，防止突发灌包撑爆下游缓冲（bufferbloat）。
>
> **轮次收尾（v4）**：后端用「LLM 结束 + 待出镜句数归 0」双条件触发 `speakingDone`，并经 `OutboundPacer.enqueueControl` 排在本轮末帧之后下发，使客户端在播放完所有真实视频帧后才进入 EOS 排空并闭嘴——避免「末帧未播」与「对话后不闭嘴」。客户端在无 `speakingDone` 时另有 `DRAIN_FALLBACK_IDLE_MS=300` 兜底，见 4.8。

### 4.8 数字人说话轮次收尾流程（v4 新增）

后端与客户端协同，确保一轮对话结束后**句末残留帧播完**并**正确恢复闭嘴待机**，根治「末帧未播」「对话后不闭嘴」两类缺陷。

```
┌─ 后端（说话轮次状态机，ChatSessionContext）─────────────────────────────┐
│                                                                          │
│  新输入/打断/语音一句话结束                                                │
│    └─ resetSpeakRound() → pending=0, llmComplete=false, enqueued=false   │
│                                                                          │
│  每句 TTS 调度  ─► beginSpeakSentence()       → pendingSpeakSentences +1 │
│  每句视频 done ─► onSpeakVideoDoneAndMaybeReady() → pending -1 → tryClaim│
│  LLM 流结束    ─► markLlmCompleteAndMaybeReady() → llmComplete=true→tryClaim│
│                                                                          │
│  tryClaimSpeakingDone():                                                  │
│    条件 = llmRoundComplete && pendingSpeakSentences==0                    │
│    通过 speakingDoneEnqueued.compareAndSet(false,true) 保证一轮只发一次    │
│    → WsMessageSender.enqueueSpeakingDone(ctx)                             │
│      → OutboundPacer.enqueueControl(speakingDone)                         │
│        (排在末帧之后，与句末 done 同序)                                    │
│                                                                          │
│  MuseTalk 编码器侧（ws_routes.py）：                                       │
│    flush 尾包 encoder.close() 一律发送，不再受 max_frames 截断             │
│    → 收口 AU（含 EOS 信息）必达客户端，避免末帧滞留编码器                   │
└──────────────────────────────────────────────────────────────────────────┘
                                   │ speakingDone（末帧之后）
                                   ▼
┌─ 客户端（AVSyncPlayer 说话状态机）──────────────────────────────────────┐
│                                                                          │
│  状态机: IDLE ──首帧──► PLAYING ──队列空+收口──► DRAINING ──EOS 排空──► IDLE │
│                                                                          │
│  RenderStateListener:                                                    │
│    onSpeakingStart()  本轮首帧渲染 → 隐藏待机视频                          │
│    onSpeakingEnd()    EOS 排空完成 / interrupt → 显示待机视频（闭嘴）     │
│                                                                          │
│  onSpeakingDone():  speakingDoneReceived=true                            │
│  shouldEnterDrain():                                                     │
│    state==PLAYING && 视频队列空 && 音频队列空                              │
│    && (speakingDoneReceived                                              │
│        || (视频静默≥300ms && 音频时钟停滞))  ← 兜底，防 speakingDone 丢失 │
│    → state=DRAINING, 向 MediaCodec 发 BUFFER_FLAG_END_OF_STREAM(EOS)     │
│  videoFeedLoop EOS 处理:                                                  │
│    收到 BUFFER_FLAG_END_OF_STREAM → 渲染剩余可显示帧 → completeDrain()    │
│    → releaseDecoder() + state=IDLE + onSpeakingEnd() → 闭嘴待机           │
│                                                                          │
│  forceStopSpeaking()（interrupt / onConversationEnd 调用）:             │
│    跳过 EOS 排空，立即 state=IDLE + onSpeakingEnd() → 立即闭嘴            │
└──────────────────────────────────────────────────────────────────────────┘
```

**设计要点：**
- **双条件触发**：仅 LLM 结束（`responseDone`）不够——可能还有句末视频在出；仅待出镜归 0 也不够——LLM 可能还在流式产句。两者同时成立才收口，避免早收口丢句、晚收口空等。
- **Pacer 同序**：`speakingDone` 经 `enqueueControl` 挂在 `OutboundPacer` 队列末帧之后，客户端收到的顺序严格是「真实视频帧 → speakingDone」，不会被突发重排到末帧之前。
- **EOS 排空**：客户端不直接依赖「队列空 = 说话完」，而是向 `MediaCodec` 发 EOS 让解码器吐出 pipeline 内残留帧（编码器/解码器各缓存若干帧），`BUFFER_FLAG_END_OF_STREAM` 出现后才真正 `completeDrain`，保证末帧可见。
- **兜底超时**：若 `speakingDone` 因网络/中断丢失，客户端在「视频静默 ≥ `DRAIN_FALLBACK_IDLE_MS`(300ms) 且音频时钟停滞」时自动进 Draining，避免永不闭嘴。
- **打断短路**：`interrupt` / `onConversationEnd` 走 `forceStopSpeaking()`，跳过 EOS 排空立即闭嘴，保证打断的即时性。

│   ├── 收口保证: encoder.close() flush 尾包一律发送，不受 max_frames 截断
│   │   （保证句末收口 AU 必达，配合客户端 EOS 排空，根治末帧未播）
│   ├── 优化: 流水线重叠、TeaCache(高相似跳 UNet)、torch.compile、FP16/TF32
│   └── 中断: cancel_flag 立即停止 + 清缓存
├── RabbitMQ Consumer
│   ├── video.preload.queue  → 下载视频 + 抽音频 + load_avatar 进 GPU
│   ├── video.delete.queue   → 清 GPU 缓存 + 删文件
│   └── video.test.queue     → 调 SoVITS /tts/offline → 离线生成测试 MP4
│   └── 状态写 Redis: digital_human:preload_status:{attraction_id}
└── 启动预加载: 扫描 BASE_VIDEO_DIR/*.mp4 → load_avatar → warmup
```

### 5.3 前端通信协议设计

#### 5.3.1 WebSocket 二进制帧协议

客户端与服务端之间通过**首字节（typeFlag）**区分二进制帧类型：

| 首字节 | 类型 | 帧结构 | 说明 |
| --- | --- | --- | --- |
| `0x01` | 音频 PCM | `[0x01][sentenceId 2B][ptsMs 4B][PCM N]`（7 字节 header） | CosyVoice 合成音频，16kHz s16le mono，客户端 AudioTrack 直接播放 |
| `0x03` | 视频帧 | `[0x03][sentenceId 2B][ptsMs 4B][keyFrame 1B][H.264 N]`（8 字节 header） | MuseTalk H.264 access unit，客户端 MediaCodec 解码渲染 |

> Java 后端在 CosyVoice 输出（7B header）基础上直接转发音频帧；在 MuseTalk 输出（7B 内层头）基础上追加 `0x03` 后转发视频帧。PTS 由后端 `PtsTracker` 将局部句内 PTS 转换为全局会话级 PTS。
>
> 控制消息（`done`、`speakingDone`）为文本帧，经 `OutboundPacer.enqueueControl()` 挂在末帧之后按 PTS 顺序释放，保证「帧 → 控制消息」到达客户端的严格先后。

#### 5.3.2 WebSocket 连接规范

```
ws://{host}:8080/ai-project/chat?token=<JWT>&attractionId=<id>[&conversationId=<uuid>]
```

- 认证：URL 参数 `token` 或 Header `Authorization: Bearer <JWT>`，由 `WSJwtHandshakeInterceptor` 握手校验
- 连接参数：`attractionId` 必填；`conversationId` 可选，用于继续历史对话
- 继续对话校验：后端确认 conversationId 属于当前用户后沿用，否则创建新会话；当前未校验旧会话与本次 attractionId 是否一致
- 服务端回执：`allDone` 携带服务端权威的 `conversationId` 与 `textOnly`
- 空闲超时：`WsIdleDetector` 每 80 秒扫描一次，超过 30 分钟无活动自动断开
- 断开时：有效会话更新消息数并创建待评价；零交互短会话保留已创建的 `IN_PROGRESS` 记录，不创建待评价
- 路线不随连接断开清理，按会话保留 12 小时，或由 `routeClose` 显式删除

### 7.1 LLM 大模型架构

#### 7.1.1 多 ChatClient 策略

后端配置多个 `ChatClient` Bean，按场景分流：

| ChatClient Bean | 用途 | 模型 | Temperature | 特性 |
| --- | --- | --- | --- | --- |
| `llmGuideChatClient` | 常规文本导游对话 | `qwen3.6-flash` | 0.8 | 挂 ChatMemory (最近10轮) + MCP 工具 (高德地图)；关闭 thinking；流式输出 |
| `vlGuideChatClient` | VL 多模态对话 (备用) | 默认 `qwen3.6-flash` | 0.7 | 挂 ChatMemory + MCP 工具；关闭 thinking；当前文本对话未使用 |
| `etlChatClient` | FAQ 标准问题生成 / 聚类分类 | `qwen3.7-max` | 0.1 | 无状态，低温度确定性输出；文档向量化由 EmbeddingModel 完成 |
| `expertChatClient` | 路线推荐 / 情感分析 / 服务建议 | `qwen3.7-max` | 0.1 | 无状态，结构化 JSON 输出 (BeanOutputConverter) |
| `emotionVisionChatClient` | 面部表情情感分类 | 默认 `qwen3.7-plus`（可配置） | 0.2 | 无状态（不挂 ChatMemory/MCP），视觉输入 → 结构化 JSON；模型由 `spring.ai.emotion.vision-model` 配置 |

#### 7.1.2 提示词组装策略（DynamicPromptService）

```
System Prompt = 基础人设
              + 用户画像 (Redis Hash: gender/age/interests/travelPurpose/guideDepth)
              + 导游偏好 (语言/风格/深度/兴趣)
              + 热点 FAQ 匹配 (Redis)
              + RAG 文档检索 Top-K (Redis Vector, 按 attractionId 过滤)
              + 对话历史 (JDBC ChatMemory, 窗口最近 10 轮)
```

### 7.2 RAG 向量检索引擎

```
文档 → MarkItDown 转换 → TokenTextSplitter (普通文本目标 800 token)
    → MarkdownTableSplitter (小表整体保留；大表按约 3000 字符拆分)
    → Spring AI Embedding (DashScope text-embedding-v4)
    → Redis VectorStore (显式 HNSW；COSINE 使用 Spring AI 默认值)
    → 检索时同模型向量化用户问题 → Top-K 相似度搜索 (按 attractionId + type 过滤)
```

### 7.3 TTS 语音合成

| 参数 | 说明 |
| --- | --- |
| 模型 | CosyVoice3 (Fun-CosyVoice3-0.5B) |
| 合成方式 | 零样本（Instruct），仅需 1 条参考音频 + 对应文本 |
| 内部/输出采样率 | 24kHz → 重采样 16kHz |
| 输出格式 | s16le PCM 单声道，含 7 字节 header（0x01/sentenceId/ptsMs） |
| 音色管理 | 按 `digital_human_id` 加载对应 `.wav`，全局共享 `prompt.txt` |
| 并发控制 | GPU 串行锁 + 单 worker 保证逐句顺序 |
| 预热 | 启动时触发首次推理，消除冷启动 |

### 7.4 数字人视频生成

| 参数 | 说明 |
| --- | --- |
| 模型 | MuseTalk (UNet + SD-VAE + Whisper-tiny) |
| 输入 | 16kHz PCM + 预加载头像视频 |
| 输出 | **H.264** 帧流 @ 25fps，每帧含 7 字节内层 header（sentenceId/ptsMs/keyFrame），Java 端追加 0x03 后共 8 字节 header |
| 推理加速 | 流水线重叠（双 CUDA Stream）、BATCH=48、TeaCache、torch.compile、FP16、TF32、H.264 线程池编码 |
| 头像缓存 | 每景点预处理一次（人脸检测 + VAE 编码）缓存于 GPU |
| **收口保证** | `encoder.close()` flush 尾包一律发送、不受 `max_frames` 截断，保证句末收口 AU 必达（v4） |
| 中断 | `cancel_flag` 立即停止当前推理 + 清缓存 |

### 7.5 路线推荐 AI（RouteRecommendationService）

```
expertChatClient (qwen3.7-max, temp 0.1) 结构化输出
    → BeanOutputConverter → RoutePlanDraft {title, summary, stops[]}
    → 每个 stop 调 AmapClient 解析坐标 (高德 POI 文本/周边检索, GCJ-02)
    → Redis 缓存 POI 结果 (amap:poi:{adcode}:{keyword}, 7天; amap:anchor:{attractionId}, 30天)
    → 解析失败优雅降级 (resolved=false, 坐标空)
    → 持久化 route:plan:{attractionId}:{userId}:{conversationId} (12h TTL)
```

- 坐标系 **GCJ-02**，与前端高德定位统一，避免坐标漂移
- 节点状态机：`UPCOMING`(未到达) → `CURRENT`(进行中) → `ARRIVED`(已到达)
- 路线生成使用独立线程池（4 线程），不借用 TTS executor，避免打断时被 shutdownNow 误杀

### 7.6 说话轮次编排（SpeakRound，v4 新增）

后端对一轮「用户输入 → 数字人说话完毕」的编排由 `ChatSessionContext` 内的说话轮次状态承担，**与 LLM/TTS/MuseTalk 三段流水线解耦**，仅做收尾仲裁。

| 组件 | 职责 |
| --- | --- |
| `pendingSpeakSentences` (AtomicInteger) | 待出镜句数计数；`beginSpeakSentence()` +1（每句调度 TTS 时）、`onSpeakVideoDoneAndMaybeReady()` -1（每句 MuseTalk `done` 时） |
| `llmRoundComplete` (volatile) | LLM 流是否结束；`markLlmCompleteAndMaybeReady()` 在 `responseDone` 后置 true |
| `speakingDoneEnqueued` (AtomicBoolean) | 一轮只下发一次 `speakingDone` 的 CAS 闸门 |
| `resetSpeakRound()` | 新输入 / 打断 / 语音一句话结束时复位三者；入口见 `AiChatHandler`(`text`/`interrupt`)、`NlsTranscriberManager`(`userInput`) |
| `tryClaimSpeakingDone()` | 双条件（`llmRoundComplete && pendingSpeakSentences==0`）成立时 `compareAndSet` 抢占，成功才允许下发 `speakingDone` |
| `WsMessageSender.enqueueSpeakingDone()` | 调用 `OutboundPacer.enqueueControl()` 把 `speakingDone` 排在末帧之后；无 Pacer 时直发（兜底） |

> 该状态机不涉及音视频内容、不修改 PTS，仅决定「何时告诉客户端可以闭嘴」，与 `PtsTracker`/`OutboundPacer`/`resetRound` 各司其职。

### 9.3 WebSocket 通信规范

- **连接路径**：`ws://{host}:8080/ai-project/chat?token=<JWT>&attractionId=<id>[&conversationId=<uuid>]`
- **心跳机制**：客户端发 `{"type":"ping"}`，服务端回 `{"type":"pong"}`；MuseTalk/CosyVoice 侧每 20s ping
- **空闲检测**：`WsIdleDetector` 每 80 秒定时扫描，30 分钟超时主动断开
- **重连策略**：客户端负责按退避策略重建；继续对话时携带历史 `conversationId`，后端校验用户归属后复用；路线按 `attractionId + userId + conversationId` 经 REST 恢复
- **历史记录**：连接建立即创建或复用 `IN_PROGRESS` 记录；断开时仅有效会话更新消息数并创建待评价，零交互短会话继续保留进行中记录
- **控制消息保序**：`done` / `speakingDone` 等文本控制帧经 `OutboundPacer.enqueueControl()` 挂在末帧之后释放，保证与音视频帧的先后顺序（v4）

## <a id="sec-10" name="sec-10">​</a>10. 安全设计
### 10.1 认证与鉴权

```
登录 → JWT Token (HS256/384/512，由密钥长度自适应) → Redis 存储 (7 天 TTL, 剩余 <24h 续期)
    → 拦截器校验 (Authorization Header / WS query token + Redis TTL)
    → ThreadLocal 上下文 (UserContext / AdminContext)
    → 请求结束自动清理
```

- 登录/注册接口白名单，不经拦截器
- 用户和管理员使用独立拦截器和上下文
- WebSocket 由 `WSJwtHandshakeInterceptor` 在握手阶段校验 token，userId 从 Token 解析

### 10.2 限流策略

- **AI 对话**：`ai:chat:{userId}` 维度，令牌桶算法，每分钟约 10 次
- **面部表情**：`ai:face-emotion:{userId}` 维度，令牌桶算法，每 5 秒最多 1 次
- **实现**：`RateLimiterUtil` + Redis 原子操作

### 10.3 数据安全

| 措施 | 说明 |
| --- | --- |
| 密码加密 | BCrypt 哈希存储；密码字段 `select=false` 不参与查询 |
| JWT 签名 | `Keys.hmacShaKeyFor()` 按密钥长度自适应选择 HS256/384/512 |
| 中间件密码 | 应通过环境变量/外部 Vault 注入 |
| OSS 访问 | RAM AccessKey，最小权限原则 |
| 数据库端口 | MySQL/Redis 仅内部访问，不暴露公网 |

> **安全提醒**：`application-dev.yml` / `application-prod.yml` 当前含硬编码凭据（阿里云 Key、DB/Redis/RabbitMQ 密码），切勿提交到公开仓库，建议迁移到环境变量或密钥管理服务。

### 10.4 输入校验

- Controller 层 `@Valid` + JSR-303 注解校验
- 全局异常处理器统一返回校验错误
- 文件上传限制格式与大小（图片 `image/*`、文档 `.doc/.docx/.pdf`、视频 `video/*`）

## <a id="sec-11" name="sec-11">​</a>11. 性能与可靠性设计
### 11.1 性能优化措施

| 层面 | 优化手段 |
| --- | --- |
| **LLM 调用** | 流式输出 + StreamingSentenceSplitter 逐句推送，降低首字延迟感知 |
| **TTS 合成** | 单线程串行执行器保证语音顺序；逐句投递不阻塞 LLM 流 |
| **数字人生成** | 双 CUDA Stream 流水线重叠、BATCH=48、TeaCache、torch.compile、FP16、H.264 线程池编码 |
| **音视频传输** | 后端纯透传不排队，Jitter Buffer/同步下放客户端 AVSyncPlayer（音频主时钟门控 lip-sync）；后端 OutboundPacer 按 PTS 时钟节拍下发视频帧防 bufferbloat |
| **轮次收尾** | `speakingDone` 双条件触发 + Pacer 末帧后保序下发 + 客户端 EOS 排空，避免末帧丢失与空等闭嘴（v4） |
| **路线 POI** | AmapClient 解析结果 Redis 缓存 (POI 7天/锚点 30天)，按 adcode/keyword 命中复用 |
| **数据库** | MyBatis-Plus 游标分页、连接池复用、索引优化、逻辑删除 |
| **缓存** | 用户画像 (6h)、FAQ 热点 (12h)、JWT (7d)、激活路线 (12h)、会话关联 (36h) |
| **消息队列** | 异步处理文档向量化、旅游历史落库、视频管理等非实时操作 |

### 11.2 会话管理

| 组件 | 职责 |
| --- | --- |
| `ChatSessionRegistry` | 全局会话注册表（ConcurrentHashMap），管理所有在线 WS 连接 |
| `ChatSessionContext` | 单会话上下文：用户 WS、MuseTalk WS、CosyVoice WS、TTS 单线程池、OutboundPacer、PtsTracker、conversationId(UUID)、提问计数、**说话轮次状态（pendingSpeakSentences/llmRoundComplete/speakingDoneEnqueued，v4）** |
| `OutboundPacer` | 出站视频帧按全局 PTS 时钟节拍下发，防止突发灌包撑爆下游缓冲（bufferbloat）；每帧发送前按 PTS 间隔 sleep；`enqueueControl()` 把控制消息（`done`/`speakingDone`）排在末帧之后（v4） |
| `PtsTracker` | 全局 PTS 偏移管理：将 CosyVoice/MuseTalk 的句内局部 PTS 转换为会话级全局 PTS，打断时复位偏移 |
| `WsIdleDetector` | 每 80 秒定时扫描，超过 30 分钟无活动主动断开释放资源 |
| **`AVSyncPlayer`（客户端）** | 音画同步播放器：音频主时钟门控 lip-sync；说话状态机 `IDLE→PLAYING→DRAINING→IDLE`，`speakingDone` 触发 `MediaCodec` EOS 排空残留帧后 `onSpeakingEnd` 闭嘴；`DRAIN_FALLBACK_IDLE_MS=300` 兜底；`interrupt`/`onConversationEnd` 走 `forceStopSpeaking()` 立即闭嘴（v4） |

### 11.3 异常处理

| 层级 | 机制 |
| --- | --- |
| Controller | 全局异常处理器 `@RestControllerAdvice`，统一返回 `Result` 错误结构 |
| WebSocket | `handleTransportError` 捕获传输异常，清理会话资源 + 通知客户端 |
| AI 服务连接 | MuseTalk/CosyVoice 连接失败记录日志，不影响主会话建立（`allDone` 仍会发送） |
| 路线降级 | 高德解析失败时节点 `resolved=false`，路线仍下发 |
| 消息队列 | Java 消费端使用自动 ACK，并配置最多 5 次重试；仅 `doc.convert.request` 显式绑定 `doc.convert.dlx` / `doc.convert.dlq`。当前 Python worker 即使转换异常也会 ACK 原消息，且 `doc.convert.result` 未绑定 DLX；Java 结果消费者捕获异常后不再抛出，因此转换失败可能不会进入 DLQ。DLQ 监听器当前只记录日志 |
| **收口兜底（v4）** | `speakingDone` 丢失时客户端按 300ms 静默 + 音频时钟停滞自动进 Draining；`speakingDoneEnqueued` CAS 保证一轮不重发 |

### 11.4 可观测性

| 维度 | 方式 |
| --- | --- |
| 应用日志 | SLF4J + Logback，关键路径埋点（会话建立、AI 调用、帧级诊断、`speakingDone`/EOS 排空日志、异常） |
| AI 服务日志 | Python logging，统一时间戳格式；MuseTalk perf 日志含 `tailFrames`（v4） |
| 容器日志 | `docker logs` 查看中间件状态 |
| 健康检查 | SoVITS `/health`，MuseTalk 启动日志验证，Redis 预加载状态键 |
