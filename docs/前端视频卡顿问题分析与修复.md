# 前端视频卡顿问题分析与修复

## 问题现象

Android 端播放数字人视频时出现严重卡顿——画面掉帧、音频断续、音视频不同步。

## 问题诊断

### 日志分析

从 `日志/前端日志.md` 的 logcat 输出中发现以下关键证据：

| 异常指标 | 观测值 | 期望值 |
|----------|--------|--------|
| WebSocket 帧接收间隔 | 1-2 秒/批 | ~40ms/帧 (25fps) |
| 视频队列深度 | 波动于 1 ~ 80 帧 | 稳定 >10 帧 |
| 音频 write() 耗时 | 3-5 秒 | <100ms |
| 音频缓冲量 | -18000ms (严重欠载) | 0~200ms |

### 根因定位

后端推理速度完全满足实时性（30 秒视频数秒内即可推理完成，并批量发送至前端），但前端队列却频繁为空。问题出在 **WebSocket 读取线程被阻塞**，导致帧已经到达后端缓冲区，但前端来不及收。

#### 阻塞链路

```
WebSocket.onMessage(ByteString)  ← OkHttp 单线程回调
    └→ mPlayer.onVideoData()     ← 入队视频帧 (LinkedBlockingQueue)
    └→ startPlayback()           ← ★ 直接在此线程调用！
            ├→ t.join(200) × 10  ← 等待旧音频线程退出，最长阻塞 2 秒
            └→ audioTrack.write() ← 写入静音帧，阻塞 3-5 秒
```

**根因 1：`startPlayback()` 在 WebSocket 回调线程上同步执行**

`startPlayback()` 被 `onVideoData()` 直接调用，而 `onVideoData()` 运行在 OkHttp 的 WebSocket reader 线程上。`startPlayback()` 内部：
- 先 `t.join(200)` 循环 10 次等待旧音频线程退出（最长 2 秒）
- 然后 `audioTrack.write(silenceFrame)` 写入大量静音帧

这导致 WebSocket 接收线程被长时间阻塞，新帧无法入队。

**根因 2：音频静音填充策略错误（核心恶性循环）**

旧代码无限制地向 AudioTrack 写入静音帧：
```java
// 旧代码：只要缓冲区未满就无脑写入，企图填满
while (audioTrack.write(silenceFrame, ...) >= 0) { ... }
```

这导致 AudioTrack 的内部缓冲被静音帧彻底填满。当后续真实音频数据调用 `audioTrack.write()` 时，必须等待硬件消费掉前面的静音数据才能写入——这就是 `audioPlayLoop` 中 `write()` 阻塞 3-5 秒的原因。

而音频线程长时间阻塞在 `write()` 中（native 层无法被 Java `interrupt()` 中断），导致 `onConversationEnd()` / `interrupt()` 中的 `t.join()` 总是超时（2 秒），进一步延长了 WebSocket 线程的阻塞时间。

```
填满 AudioTrack → 真实音频 write() 阻塞 3-5s
    → 音频线程卡在 native 层，join() 总是超时 2s
    → startPlayback() 阻塞 WebSocket 线程 2s+
    → 新帧收不进来 → 队列耗尽 → 卡顿
```

**根因 3：视频缓冲阈值太小**

- `VIDEO_BUFFER_THRESHOLD = 25`（仅 1 秒），而后端是批量突发发送（间隔 1-2 秒）
- `VIDEO_QUEUE_MAX = 80`（3.2 秒），突发大量帧时空问不足

**根因 4：每个二进制包都打 Log.d**

`ChatActivity.onMessage(ByteString)` 对每个收到的音频/视频包都打印日志，logcat I/O 在高频下（25fps 视频 + 音频包）成为额外开销。

## 修复方案

### 文件：`AVSyncPlayer.java`

#### 修复 1：`startPlayback()` 异步化（行 ~214）

**问题**：在 WebSocket 回调线程上直接调用 `startPlayback()`

**修改**：
```java
// 旧代码
if (!playbackStarted && videoQueue.size() >= VIDEO_BUFFER_THRESHOLD) {
    playbackStarted = true;
    startPlayback();  // ← 阻塞 WebSocket 线程
}

// 新代码
if (!playbackStarted && !released && videoQueue.size() >= VIDEO_BUFFER_THRESHOLD) {
    playbackStarted = true;  // 提前标记，避免重复提交
    decoderExecutor.submit(this::startPlayback);  // ← 异步执行
}
```

#### 修复 2：增大缓冲阈值（行 37, 188）

```java
// 旧值
private static final int VIDEO_BUFFER_THRESHOLD = 25;   // 1 秒
private static final int VIDEO_QUEUE_MAX = 80;           // 3.2 秒

// 新值
private static final int VIDEO_BUFFER_THRESHOLD = 75;    // 3 秒
private static final int VIDEO_QUEUE_MAX = 200;          // 8 秒
```

- 3 秒起始缓冲：吸收后端 1-2 秒的突发间隔
- 8 秒队列上限：容纳大量 burst 帧而不丢帧

#### 修复 3：智能静音填充（行 ~358-366）

**问题**：无脑填满 AudioTrack 缓冲区，阻塞后续真实音频写入

**修改**：
```java
// 旧代码：无限制写入静音帧
while (audioTrack != null && audioTrack.getPlayState() == AudioTrack.PLAYSTATE_PLAYING) {
    if (audioQueue.isEmpty()) {
        audioTrack.write(silenceFrame, 0, silenceFrame.length);  // 无脑填
    }
}

// 新代码：仅在缓冲不足时写入
if (audioQueue.isEmpty()) {
    long headPos = audioTrack.getPlaybackHeadPosition();
    long bufferedSamples = audioTotalSamples - headPos;
    long bufferedMs = Math.max(0, bufferedSamples) * 1000 / AUDIO_SAMPLE_RATE;
    if (bufferedMs < 80) {  // 仅保持 ~80ms 缓冲
        audioTrack.write(silenceFrame, 0, silenceFrame.length);
        audioTotalSamples += silenceFrame.length / 2;
    }
}
```

**关键**：`AUDIO_SAMPLE_RATE = 16000`，80ms 缓冲仅需 `16000 * 0.08 * 2 = 2560` 字节（约 1280 个 sample），而不是填满整个 AudioTrack 缓冲区（通常 8-32KB）。

#### 修复 4：移除阻塞 join()（行 ~218-240, 263-287）

**问题**：`onConversationEnd()` 和 `interrupt()` 通过 `t.join()` 等待音频线程退出

**修改**：
```java
// 旧代码
int retry = 0;
while (audioThread != null && audioThread.isAlive() && retry < 10) {
    audioThread.join(200);
    retry++;
}
// generation++ 后

// 新代码
// ★ generation++ 已足够让旧线程退出循环，不再 join 等待阻塞调用线程
// startPlayback() 会处理残余线程的清理
generation++;
```

`generation++` 配合线程内部的 generation 检查，使旧线程在下一次循环迭代时自动退出。不再需要调用线程等待。

### 文件：`ChatActivity.java`

#### 修复 5：日志限频（行 ~695-715）

**问题**：每个二进制包都打印 Log.d

**修改**：
```java
// 新增字段
private int binaryMsgCount = 0;

// onMessage(ByteString) 中
binaryMsgCount++;
if (binaryMsgCount % 50 == 1) {  // 每 50 个包才打一次
    Log.d("BINARY", "收到二进制数据 #" + binaryMsgCount + "，长度=" + payload.length);
}
// 移除音频包的逐条日志
```

## 修复效果预期

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| WebSocket 帧接收间隔 | 1-2s（批量堆积） | ~40ms（持续 25fps） |
| 视频队列深度 | 1 ~ 80，频繁触底 | 稳定 >10 |
| 音频 write() 耗时 | 3-5 秒 | <100ms |
| 线程阻塞 | startPlayback 阻塞 Receiver 2-5s | 异步提交，不阻塞 |
| 静音策略 | 填满 AudioTrack（恶性循环） | 仅保持 80ms 缓冲 |

---

## 关键设计原则

1. **WebSocket 回调线程只收发，不做 IO**：所有阻塞操作（解码、音频写入、线程等待）一律异步化
2. **AudioTrack 缓冲只保持最小量**：静音填充的目标是防止 underrun，而非填满缓冲区
3. **generation 计数器 > join() 等待**：用代数检查让线程自然退出，避免调用方阻塞
4. **日志是 IO**：高频路径上的日志也是性能开销
